# خطة تنفيذ آفاق (AFAQ) — مرحلة بمرحلة

راجع أولًا `docs/SOURCE_FINDINGS.md` — القرارات هنا مبنية على ما تم التحقق منه فعليًا هناك.

## المرحلة 0 — تم في هذا التسليم
- فحص فعلي لمصدر القرآن (Quranpedia) وتوثيق الـ API الرسمي والترخيص.
- محاولة فحص Dorar.net (لم تنجح من داخل بيئة هذه المحادثة — راجع القيود أدناه).
- نموذج البيانات (`models.py`) مطابق لمواصفة المستند حرفيًا.
- قواعد الثقة المفروضة كودًا (`trust.py`) بدل أن تكون تعليقات توثيقية فقط.
- عميل Quranpedia + سكربتا استيعاب (قرآن + تفسير) يعملان على الـ API الموثّق.
- باني إجابة A-G (`answer_builder.py`) + نقطة API واحدة (`/verse/{surah}/{ayah}`).
- واجهة Next.js RTL أولية تستهلك تلك النقطة وتُفصل الأقسام بصريًا (شارة حمراء صريحة
  على كل "مقارنة محتملة").
- اختبارات pytest تعمل بلا شبكة (محاكاة)، تغطي: التخزين الحرفي للنص، عدم التكرار،
  رفض الترقية الصامتة بين فئات الثقة، إلزامية المصدر، تصنيف المقارنات المحتملة.

## قيود هذه الجلسة تحديدًا (وليست قيودًا دائمة على المشروع)
- بيئة bash هنا بلا اتصال شبكي خارجي → لم يتم فعليًا استدعاء `api.quranpedia.net`
  أو تشغيل Docker/Postgres أو تنفيذ `pytest` هنا. الكود صحيح بنيويًا لكنه **غير مُختبر تشغيليًا
  بعد**. نفّذ ذلك في Claude Code أو أي بيئة بشبكة فعلية كخطوة أولى فورية.
- أداة `web_fetch` المتاحة لهذا المساعد لا تفتح رابطًا إلا إذا ظهر أولًا في نتيجة بحث — هذا منع
  فحص بعض صفحات Dorar.net مباشرة رغم محاولات بحث متعددة.

## المرحلة 1 — التحقق والتشغيل الفعلي (Claude Code)
1. `docker compose up -d db` ثم `pip install -r requirements.txt -r requirements-dev.txt`.
2. `pytest` — يجب أن تمر كل الاختبارات الحالية بلا شبكة، كدليل أساسي أولي.
3. `python -m app.ingestion.ingest_quran --surah 1` فعليًا — تحقق من أن الرد مطابق لما يعرضه
   `quranpedia.net/ayahs` نفسه يدويًا لنفس الآيات (تدقيق بشري لعيّنة لا تشغيل أعمى).
4. أعد فحص `https://dorar.net/tafseer/`, `/article/1955`, `/refs/tafseer` بشبكة فعلية:
   - اقرأ `robots.txt` وأي صفحة API/شروط استخدام.
   - إن وُجد مسار وصول مسموح → أضف `dorar_client.py` موازيًا لـ `quranpedia_client.py` بنفس الانضباط
     (توثيق كل Endpoint، احترام حدود المعدل، تخزين `source_url` و`retrieval_date`).
   - إن لم يوجد → وثّق ذلك في `SOURCE_FINDINGS.md` واستمر بكتب تفسير Quranpedia كمصدر أساسي،
     مع إبقاء الباب مفتوحًا لإضافة Dorar لاحقًا دون إعادة تصميم (بنية `Source`/`TafsirEntry`
     تدعم ذلك مباشرة).

## المرحلة 2 — الربط المعرفي والبحث
- تنفيذ `Concept` و`ScientificEvidence` فعليًا (الجداول موجودة، الربط البرمجي غير مكتمل بعد).
- أوضاع البحث الخمسة المطلوبة في المستند (بحث قرآني، تفسيري، علمي، مفاهيمي، استكشاف متعدد المصادر).
- تضمين Embeddings (pgvector) لمحتوى التفسير والمفاهيم العلمية لدعم RAG الحقيقي بدل التطابق الحرفي.

## المرحلة 3 — allowlist العلمي + LLM Synthesis
- تحديد `SCIENTIFIC_SOURCE_ALLOWLIST` بالتشاور مع صاحب المشروع (نطاقات/مؤسسات محددة).
- تفعيل طبقة LLM (Anthropic/OpenAI عبر مجردة موفر) **فقط** لصياغة القسم D ولإنشاء جسر لغوي قصير
  في القسم هـ — ممنوع إنشاء تفسير أو نص قرآني أو اقتباسات. يُطبَّق هذا كاختبار اصطناعي (adversarial)
  وليس فقط كتوجيه نصي.

## المرحلة 4 — الاختبارات العدائية والتصلّب ضد الهلوسة
نفّذ كل الأمثلة العدائية المذكورة في المستند كاختبارات pytest حقيقية ضد نقطة `/verse` ومسار الدردشة
المستقبلي: طلب حديث غير موثّق، طلب نص تفسير غير موجود، سؤال "هل يثبت هذا الاكتشاف أن..." إلخ.
